## 1. An example of the ANS algorithm

This example was from [Andrew Polar's blog post](http://www.ezcodesample.com/abs/abs_article.html). It demonstrates a very basic ANS mechanism. A [demo](http://www.ezcodesample.com/abs/ANSCoder.txt) was also provided. 

### Initial setup

1. We predefine a value `11111` (5'd31) to help indicate when the algorithm terminates. We will start encoding from this value, and end decoding after reaching this value. 
2. Suppose we want to encode and decode the following sequence of characters: `A B A C` (ideally the number appearance of each symbol should match the frequency distribution in the encoding table but that would make the process too long). 
3. We also assume that the following encoding table has been given, and both the encoder and decoder has access to this same table (We'll discuss how an encoding table can be built later): 

| state | A   | B   | C   |
| ----- | --- | --- | --- |
| 1     | 2   | 3   | 5   |
| 2     | 4   | 6   | 10  |
| 3     | 7   | 8   | 15  |
| 4     | 9   | 11  | 20  |
| 5     | 12  | 14  | 25  |
| 6     | 13  | 17  | 30  |
| 7     | 16  | 21  |     |
| 8     | 18  | 22  |     |
| 9     | 19  | 26  |     |
| 10    | 23  | 28  |     |
| 11    | 24  |     |     |
| 12    | 27  |     |     |
| 13    | 29  |     |     |
| 14    | 31  |     |     |

In this table, the leftmost column provides 14 states, and the rest 3 columns indicates the 3 possible symbols to be encoded. The main body of the table represents what we can consider as "the next state". 

So, each cell in this table provides a unique state transition, for example, the cell at 8th row in column `B` means "if we are currently in state 8 and we want to encode a symbol `B`, we'd move to state 22". And in the decoder point of view: "if we are currently in state 22, we'd decode a symbol `B` and our next state would be 8". 

### Encoding process:

The encoding process follows the following pseudo code: 

```
0. initialisation: 
    symbols_to_encode = string input
    current_state = 5'b11111

1. while symbols_to_encode is not empty: 
    2. next_symbol = the first symbol from the string to be encoded

    3. if current_state is in the "state" column: 
        4. go to row current_state, column next_symbol
        5. new current_state = cell value

    6. else (current_state is larger than the state threshold): 
        7. push the rightmost bit value of current_state into output
        8. current_state >>= 1
        9. if the new current_state exists in the "state" column: 
            goto step 3
        10. else (current_state still larger than state range): 
            goto step 6

    11. goto 1

12. now that symbols_to_encode is empty: 
    13. push everything in current_state into output
    14. return output 
```

We can try this example, step by step: 

0. Symbol to encode is `A B A C`, current state is `11111` (31 in decimal)

1. 31 (`11111`) doesn't exist in the state column
    - output `1`, `11111 >> 1` becomes `1111` (15 in decimal)
    - symbol to encode: `A B A C`
    - current output: `1`

2. 15 (`1111`) still doesn't exist in the state column
    - output `1`, `1111 >> 1` becomes `111` (7 in decimal)
    - symbol to encode: `A B A C`
    - current output: `11`

3. go to row 7, next symbol to encode is `A`
    - read from this cell, the next state is 16 (`10000`)
    - symbol to encode: `B A C`
    - current output doesn't change

4. 16 (`10000`) doesn't exist in the state column
    - output `0`, `10000 >> 1` is `1000` (8 in decimal)
    - symbol to encode: `B A C`
    - current output: `110`

5. go to row 8, next symbol to encode is `B`
    - the next state is 22 (`10110`)
    - symbol to encode: `A C`
    - current output doesn't change

6. 22 (`10110`) doesn't exist in the state column
    - output `0`, `10110 >> 1` becomes `1011` (11 in decimal)
    - symbol to encode: `A C`
    - current output: `1100`

7. go to row 11, next symbol to encode is `A`
    - the next state is 24 (`11000`)
    - symbol to encode: `C`
    - current output doesn't change

8.  24 (`11000`) doesn't exist in the state column
    - output `0`, `11000 >> 1` gives `1100` (12 in decimal)
    - symbol to encode: `C`
    - current output: `11000`

9. go to row 12, next symbol to encode is `C`
    - this cell is empty, we have to push 1 more bit into the output 
    - output `0`, `1100 >> 1` is `110` (6 in decimal)
    - symbol to encode: `C`
    - current output: `110000`

10. go to row 6, still column `C`
    - the next state is 30 (`11110`)
    - symbol to encode: (empty)
    - this is the final symbol, output everything (`11110`)
    - current output becomes `11000011110`

11. Finish encoding with output value `11000011110`


### Decoding process:

Decoding follows the following pseudo code: 

```
0. initialisation: 
    Take the 5 rightmost bits from string_to_decode to form current_state
        current_state = string_to_decode[-5:]

1. while current_state is not 11111: 
    2. while current_state is less than 5 bits: 
        3. take the last bit from string_to_decode 
            (pop this bit out as we don't need it anymore)
        4. concat it at the end of current_state
        5. goto 2

    6. find table cell with value = current_state: 
        - the column of this cell is the decoded symbol
        - the row value (under state column) of this cell is the next current_state

    7. goto 1

8. now that current_state is 11111
    - from our assumption, this means we have reached the end of decoding
    - the string_to_decode should also be empty now
    - note that the symbols were decoded backwards
```

To decode the previous example: 

0. string to decode is: `11000011110`
    - take the last 5 bits as current state: `11110` (30 in decimal)
    - string to decode becomes: `110000`
    
1. lookup 30 in our table, we get row 6, column `C`
    - output `C`, our next state is 6 (`110`)
    - current output: `C`

2. extract bits from string to decode to make our state 5 bits
    - extract 1 bit: we get `1100` (remaining string `11000`)
    - extract 1 bit (again): `11000` (remaining string `1100`)
    - `11000` is 5 bits, we stop extracting for now, this is 24 in decimal
    - string to decode: `1100`
        
3. lookup 24, we get row 11, column `A`
    - output `A`, new state is 11 (`1011`)
    - current output: `C A`

4. extract bits from string to decode
    - extract 1 bit: current state becomes `10110` (22 in decimal)
    - string to decode: `110`
        
5. lookup 22, we find row 8, column `B`
    - output `B`, new state is 8 (`1000`)
    - current output: `C A B`

6. extract bits from string to decode
    - extract 1 bit: current state becomes `10000` (16 in decimal)
    - string to decode: `11`
        
7. lookup 16, this is on row 7, column `A`
    - output `A`, new state 7 (`111`)
     - current output: `C A B A`
        
8. extract bits from string to decode to make our state 5 bits
    - extract 1 bit: we get `1111` (remaining string `1`)
    - extract 1 bit (again): `11111`

9. we have hit the terminator string, the remainder string is now empty
    - remember the decoded symbols are in reverse order, we return `A B A C`


## 2. Discussion 

After seeing the basic algorithm of an ANS coder, I thought a bit more about it before moving on to FSE (which is basically an advanced version of ANS). 

Like other lossless compression algorithms, the fundamental goal of ANS is to minimise the average number of bits per symbol (ie. to be as close to the theoretical Shannon limit as possible). 

The theoretical lower bound for encoding a message without loss (Shannon entropy):

$$
H(X) = -\sum_{i} P(x_i) \log_2 P(x_i)
$$

### ANS state transformation

Unlike Huffman coding (encodes each symbol independently) or Arithmetic coding (updates a fractional range), the idea of ANS is to perform state transitions. 

During the encoding/decoding procedure, ANS maintains a single integer state. Each time we encode/decode a symbol, the state gets updated. So, as long as we know the encoding table and our current state, we can decode the symbols in the same but reversed order as they were encoded, simply by referring to the table and performing each state transition in reverse direction (given that the encoding table is well-designed and provides a one-to-one mapping for the state transitions). 

The key take away here is that **state dynamically increases when encoding, and shrinks during decoding**. We can see this trend from the above example as well: 

- During encoding, if the state exceeds the maximum state threshold, we output some bits, reduce the state value until they are back in the range. 
- During decoding, if the state is below the desired bit length, we append bits from the encoded data stream to our state until it is within the valid range.

When the state value does not cross the boundary, it simply shifts to the next state without triggering an additional bit. This is the behaviour that contributes to the efficient compression in this algorithm. 

Also, this design enabled the coder to function by performing bit shifting, thus it doesn't require expensive floating-point arithmetic during these transformations. 

### What makes a good encoding table

We have yet to design the algorithm for building our encoding table (I want to address this when discussing the approach in FSE). However, it's not hard to realise intuitively that:

1. we'd want the most frequent symbols to occupy the most states in the encoding table. 

    (ie. In our example, column `A` should be the longest since it appeared the most times. )

    This would ensure that the most frequent symbols are more likely to have a valid state during state transitions, thus reducing the need to append additional bits to the output when encoding them. For the least frequent symbols, we may even need to append more than one bit into the output when encoding them, and this is acceptable since there are only very few such symbols.

2. The symbols should be evenly distributed across the entire state range. 

    (ie. instead of having `2 3 4 5 ...` as states for symbol `A`, we used something more evenly like `2 4 7 9 12 ...`.)

    The reason for this is that the decoder always has to map a given state to a symbol. If symbols are clustered too closely together in the state space, the decoder may need to adjust the state value more significantly to find the next symbol, which increases the overhead in terms of fractional bits. 

    For example, if a symbol appears 25% of the time, it should ideally be assigned a state every 4 positions in the table. While it's not always possible to distribute states perfectly evenly due to integer constraints, rounding up or down during state assignment won’t affect the correctness of the compression. The only downside is a slight increase in the number of bits needed compared to the theoretical Shannon entropy limit due to the rounding.

## 3. Optimisation

As mentioned before, our basic design works but would consume a long time building the encoding table if we just fill the entire table in a straightforward loop. In this section I tried to understand how FSE design provided an optimised implementation by: 
1. speeding up the generating of the encoding table, 
2. getting our next state by reading from a **specific index** instead of handling the entire table. 

(Collet wrote about this in [his last 4 posts in this series](https://fastcompression.blogspot.com/2013/12/finite-state-entropy-new-breed-of.html) but I still spent quite some time in the rabbit hole to understand this omg ;-; ) 

### Number of states to allocate (for each symbol)

We want to make the most of our encoding table within its limited length, meaning that if we use states with bit length $n$, we want to have all $2^n$ possible state transitions in our table. 

We can see that the ANS example we've been using so far is not optimal. Knowing the frequency distribution of the 3 symbols, the optimal number of states for them should be: 

| symbol |frequency | number of states <br> (ie. normalised count) |
| -----  |-----  | ---------- |
| 41     | 14    | 16         |
| 42     | 10    | 10         |
| 43     | 6     | 6          |

Note $16 + 10 + 6 = 32 = 2^5$, this gives the maximum pairs of one-to-one transitions using 5-bit state values. This was done by doing a normalisation of the frequency count in the code implementation. 

We've discussed in section 2, since state 0 - 31 would never be reached, we will allocate states 32 - 63 in our encoding table, `A` `B` `C` will get 16, 10, and 6 seperately. 

### Spreading the states

FSE focuses on providing a fast compression algorithm with a "good enough" compression ratio. While not being the theoretical best distribution, the benefit is that it can be achieved by looping through the list only once, and resulting in a fairly efficient distribution.

This idea is realised in the following 3 steps: 

1. Create a list of cumulative counts for each symbol at their respective indices.

    ```
    symbol         : 0 1 2 ... 41 42 43 44 ...
    cumulative count: 0 0 ...   0  16 26 32 32 ... 
    ```

    This is a list we use to track the index at which we should next put a state value into. eg. for symbol 41, we want to append value from 0.

2. Distribute a list `symbolTable` using a pseudo-even distribution mechanism.

    FSE uses the formula `nextState = (currentState + (5/8) * tableSize + 3 ) % tableSize` to jump from one index to the next. This can be implemented using bit shifting (like one of those pseudo random equations). It gives a list of index like: 

    ```
    0 23 14 5 28 19 10 1 24 15 6 29 20 11 2 25 16 7 30 21 12 3 26 17 8 31 22 13 4 27 18 9
    ```

    While jumping through these indices, the first 16 indices will be assigned with symbol `A`, the next 10 indices with symbol `B`, and the final 6 indices with symbol `C`: 

    ```
    16 A's at: 0 23 14 5 28 19 10 1 24 15 6 29 20 11 2 25 
    10 B's at: 16 7 30 21 12 3 26 17 8 31 
    6 C's at: 22 13 4 27 18 9
    ```

    In the end, our filled `symbolTable` would look something like: 

    ```
    Symbol Table:
    41 41 41 42 43 41 41 42 42 43 41 41 42 43 41 41 42 42 43 41 41 42 43 41 41 41 42 43 41 41 42 42 
    ```

3. Adding state values for `symbolTable`

    Since the symbol table has been well spreaded, we allocate states 32 - 63 to the corresponding symbol directly: 

    ```
    symbol table     : 41 41 41 42 43 41 41 ...
    states to allocate: 32 33 34 35 36 37 38 ...
    ```

    But this is not convenient to use as the symbols are in random order now. To quickly re-arrange the list, we use `cumulativeCounts`. For each symbol in `symbolTable`, `cumulativeCounts[symbol]` provides the index where we should place the next state in `stateTable`. 
    
    For example, say we are due to allocate state 36, `symbolTable` suggests that the state is assigned to `C`, we check the value at `cumulativeCounts[43]` and immediately know that this state value should be put at index 26 in the `stateTable`. After writing `stateTable[26] = 36`, we add `cumulativeCounts[43]` by 1 so that the next state value for `C` would be written at index 27. 

    We finish building the state table with: 

    ```
    State Table:
    32 33 34 37 38 42 43 46 47 51 52 55 56 57 60 61 35 39 40 44 48 49 53 58 62 63 36 41 45 50 54 59 
    ```

    Or, in the more familiar format, the encoding table looks like: 

| state | A   | B   | C   |     | (contd. ) | state | A   | B   | C   |
| ----- | --- | --- | --- | --- | --------- | ----- | --- | --- | --- |
| ...   | ... | ... | ... |     |           | 21    | 42  |     |     |
| 6     |     |     | 36  |     |           | 22    | 43  |     |     |
| 7     |     |     | 41  |     |           | 23    | 46  |     |     |
| 8     |     |     | 45  |     |           | 24    | 47  |     |     |
| 9     |     |     | 50  |     |           | 25    | 51  |     |     |
| 10    |     | 35  | 54  |     |           | 26    | 52  |     |     |
| 11    |     | 39  | 59  |     |           | 27    | 55  |     |     |
| 12    |     | 40  |     |     |           | 28    | 56  |     |     |
| 13    |     | 44  |     |     |           | 29    | 57  |     |     |
| 14    |     | 48  |     |     |           | 30    | 60  |     |     |
| 15    |     | 49  |     |     |           | 31    | 61  |     |     |
| 16    | 32  | 53  |     |     |           |       |     |     |     |

### Doing a state transition

In this part we want to be able to know what the next state should be, given any state and symbol during the encoding process. And the punch line here is that **you don't need to store a full table per symbol, just knowing the threshold is enough**. 

Why is this possible? we take `C` as an example and make the following observations. We start by an index of the state distribution for it's the most straightforward way of dividing the 32-state range. 

| State distribution index                       | 0 - 3   | 4 - 7   | 8 - 11  | 12 - 15  | 16 - 23  | 24 - 31 |
| ---------------------------------------------- | ------- | ------- | ------- | -------- | -------- | ------- |
| current state value subrange <br> (index + 32) | 32 - 35 | 36 - 39 | 40 - 43 | 44 -  47 | 48 -  55 | 56 - 63 |
| subrange length                                | 4       | 4       | 4       | 4        | 8        | 8       |
| output bits<br> (till state falls in threshold)| >> 2    | >> 2    | >> 2    | >> 2     | >> 3     | >> 3    |
|                                                | **8**   | **9**   | **10**  | **11**   | **6**    | **7**   |

Reordering using the last row of this table gives:

| State distribution index                        | 16 - 23  | 24 - 31 | 0 - 3   | 4 - 7   | 8 - 11  | 12 - 15  |
| ----------------------------------------------- | -------- | ------- | ------- | ------- | ------- | -------- |
| current state value subrange <br> (index + 32)  | 48 -  55 | 56 - 63 | 32 - 35 | 36 - 39 | 40 - 43 | 44 -  47 |
| subrange length                                 | 8        | 8       | 4       | 4       | 4       | 4        |
| output bits<br> (till state falls in threshold) | >> 3     | >> 3    | >> 2    | >> 2    | >> 2    | >> 2     |
| **state transition domain**                     | **6**    | **7**   | **8**   | **9**   | **10**  | **11**   |

Note that this last row gives us the value for symbol `C`'s states in the "state" column. In fact, the state would always start with the value of the frequency for each symbol. 

Add the corresponding state values from the state table: 

| State distribution Index                       | 16 - 23  | 24 - 31 | 0 - 3   | 4 - 7   | 8 - 11  | 12 - 15  |
| ---------------------------------------------- | -------- | ------- | ------- | ------- | ------- | -------- |
| current state value subrange <br> (index + 32) | 48 -  55 | 56 - 63 | 32 - 35 | 36 - 39 | 40 - 43 | 44 -  47 |
| subrange length                                | 8        | 8       | 4       | 4       | 4       | 4        |
| bits output                                    | >> 3     | >> 3    | >> 2    | >> 2    | >> 2    | >> 2     |
| **current state after output**                 | **6**    | **7**   | **8**   | **9**   | **10**  | **11**   |
| **next state index in `stateTable`**           | **26**   | **27**  | **28**  | **29**  | **30**  | **31**   |
| next state value                               | 36       | 41      | 45      | 50      | 54      | 59       |

We can see that the offset between the state and the index of the next state value in `stateTable` is always the same for a given symbol. We can thus use this value to directly go to the next index of the next state. 

We store 20 as our `nextStateOffset` value for symbol `C`. Now, if we are to encode a symbol `C`, we'd simply go to index `nextStateOffset + currentState` in the state table to get our new state. 

Note that for the first symbol(s) this value would be negative. For example, the state of `A` starts at 16, while the index for it in the state table is 0, we have an offset of -16.
